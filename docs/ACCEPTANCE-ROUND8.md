本批确认并修复了一个验收缺陷：[旧第二次失败记录](qa/round7/core-second-attempt.json) 的首个短按实际约 510.4 ms、落点 `hit=3`，但“Short pointer charge: current-platform landing preserves score”已经被记录为通过。原检查只看回位后的分数、跳数和平台；无敌救回也能满足这些结果。

## 小样本对照设计

新增 `qa-resource-diagnostic.cjs`：录屏开/关 × 移动加载前保留/关闭桌面上下文，共四格，每格一个独立 Chromium 浏览器。桌面保持原测试的 414×736 输入条件，加载/重载后执行两次真实 50 ms 指针请求和一次 720 ms 按键请求；随后切到 1440×900 主页，再执行保留/关闭因素，加载 390×844 移动页面并进行真实触摸长按和无敌回位。

保留/关闭因素在桌面输入之后应用，因此不能用它解释之前的桌面输入偏差。每格只有一次移动加载，不作统计显著性、稳定性保证或“未复现即不存在”的结论。各条件顺序、环境、最终产品和脚本摘要均保留在 [原始结果](qa/round8/matrix-results.json)。环境为云端 Chromium/SwiftShader、Node 24、4 核配额，结论不外推到实体设备。

| 桌面录屏 | 移动加载时桌面上下文 | `goto(load)` | 正文接收结束* | 移动页面最长主线程任务 |
| --- | --- | ---: | ---: | ---: |
| 关 | 关闭 | 1.336 s | 114.2 ms | 714 ms |
| 开 | 保留 | 8.961 s | 143.8 ms | 8188 ms |
| 关 | 保留 | 7.454 s | 133.0 ms | 6802 ms |

*正文时间为浏览器 Navigation Timing 相对导航开始的 `responseEnd`，不是整个启动时间。每格另有同期 Node HTTP 完整 GET，均为 200、响应摘要与产品一致；同期 GET 约 39–70 ms。保留的桌面页面始终可见，期间任务计数继续增加，并非已停止的空上下文。CPU、堆、主线程任务和帧间隙也有记录。

本次明显的耗时发生在正文到达后的页面任务阶段；保留桌面条件下观察到更长的主线程任务及更多 GPU 进程 CPU 时间，**支持资源竞争是本次慢加载的线索**。没有获取具体阻塞函数的火焰图，也没有重现原先 30 秒超时，因此不把它写成已确认根因。录屏开启且桌面关闭的一格比关闭录屏的一格更快，也不能将录屏单独判为原因。

四格共 12 次桌面输入的实际落点检查，以及 4 次移动加载/触控回位均通过。未扩大为反复无差别全量测试。

## 输入时序观察

`qa-telemetry.cjs` 保留宿主单调时钟和墙钟、down/wait/up 请求的开始/结束、浏览器事件时间戳、捕获与处理后时刻、产品实际消费的 `flight.hold`、长任务及 RAF 间隙。真实输入仍按原来的 down → `page.waitForTimeout` → up 执行；没有根据请求时间修正产品收到的长按。

- 录屏关闭、桌面随后关闭的一格：720 ms 请求的等待 RPC 实际约 790.6 ms，产品实际约 796.6 ms；期间没有记录到超过 50 ms 的页面长任务。这提示宿主/自动化等待调度也可能带来偏差，不能把所有偏差归于录屏或页面阻塞。
- 录屏开启、桌面随后关闭的一格：50 ms 请求的事件时间戳间隔约 59.4 ms，捕获间隔约 119.2 ms，产品实际约 115.6 ms。松开事件从时间戳到捕获约延迟 60.6 ms，同窗口出现 69 ms 页面长任务、约 66.6 ms RAF 间隙，up 请求等待约 64.0 ms。这是本次观察到的**事件排队与消费延迟**，该次仍确实命中当前平台。

这些观测解释了本次较小偏差发生的阶段，不能追溯证明旧 510 ms 样本的原因；旧样本缺少相应时序数据，原始记录保持不变。
